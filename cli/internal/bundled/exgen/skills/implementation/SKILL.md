# Implementation

Execute a structured prompt (generated by the `structured-prompt` or `user-story` skills) as working, tested code. The prompt file is the **contract**: Scope In is the definition of done, Scope Out is a hard boundary, the Approach is a binding design decision, Operations are the execution order, and Safeguards are invariants that must hold — and be tested — when you finish.

Development is strict TDD: no production code without a failing test first.

## Reference file

**`references/testing-anti-patterns.md`** — read it before writing your first test, and re-check it any time you are about to add a mock or feel tempted to add a test-only method to production code. Its gate functions are part of this workflow, not optional advice.

## Workflow

### 1. Locate and read the prompt

Resolve `$ARGUMENTS` to a file in `spdd/prompt/`:
- An id like `001` or `JIRA-123` → the file whose name starts with it
- A path → that file
- Nothing given → the lowest-numbered prompt in `spdd/prompt/`; confirm the pick with the user before starting

Read the entire prompt. Then verify its **dependencies**: if Scope In or Safeguards reference earlier tasks ("uses the RateLimiter introduced in 001"), confirm that code exists in the codebase. If a dependency is missing, stop and tell the user which prompt must be implemented first.

### 2. Ground the prompt in the codebase

Read the files the prompt implies: the entities it marks EXISTING, the services/handlers named in Operations, the test setup and conventions of neighboring tests. This is targeted reading, not a full scan — the prompt tells you where to look.

If reality contradicts the prompt — an EXISTING entity doesn't exist, a named method has a different signature, an Operation is impossible as written — **stop. Do not silently improvise.** Report the mismatch, propose the smallest amendment to the prompt, and get the user's confirmation. The prompt is the review surface the user approved; code that drifts from it defeats the whole system.

### 3. Plan the test map

Before writing anything, map what will prove the work is done:
- Each **Operation** → the test(s) that will drive it
- Each **Safeguard** → at least one test that would fail if the safeguard were violated (skip only if genuinely untestable, e.g. a code-review-only rule — say so)
- Each **Scope In** item → which test or observable behavior demonstrates it

Keep this map as your todo list. It becomes the completion report in step 5.

### 4. TDD loop — one Operation at a time

Take Operations strictly in their numbered order. For each:

1. **Red** — write the failing test for this Operation's behavior. Run it and watch it fail *for the right reason* (the behavior is missing), not because of a typo or setup error. A test you never saw fail proves nothing.
2. **Green** — write the minimal production code to pass. Minimal means: no fields, methods, or branches the current test doesn't force into existence. Resist implementing ahead of the Operations list.
3. **Refactor** — clean up while all tests stay green. Follow the conventions found in step 2, not your own preferences.
4. Run the **full** test suite, not just the new test. Green across the board before starting the next Operation.

Rules that hold throughout the loop:
- **Scope Out is a wall.** If an Operation seems to need something Scope Out excludes, that's a step-2-style contradiction — stop and raise it.
- **Mocks follow the gate functions** in the anti-patterns reference: understand side effects before mocking, mock at the lowest level that isolates the slow/external part, mirror real data structures completely, and never assert on a mock's existence.
- **No test-only methods in production classes.** Cleanup helpers live in test utilities.
- Safeguard tests are written at whichever Operation makes them testable — do not defer them all to the end.

### 5. Verify and report

When the last Operation is done:

1. Run the full suite one final time.
2. Walk the Scope In list and the Safeguards list item by item, and produce a short **completion report** in chat:
   - Each Scope In item → the test/behavior that proves it ✓
   - Each Safeguard → the test that enforces it ✓ (or the stated reason it's untestable)
   - Any deviations that were approved along the way, and any (ASSUMPTION) markers from the prompt that the implementation had to resolve
3. Anything unproven is not done. "Implementation complete, ready for testing" is a forbidden sentence — tests *are* the implementation (anti-pattern 5).

### 6. Hand off to review — the mandatory gate

Ask the user to confirm the report, then invoke the `review` skill (this plugin: `/exgen:review`) on this prompt. Review is not optional: the prompt file **stays in `spdd/prompt/` until the review verdict is APPROVE** — only the review moves it to `spdd/done/`. Do not move the file yourself, and never claim the task is done on the strength of your own completion report; the self-report is input to the gate, not the gate.

On **REQUEST CHANGES**: treat each blocking finding as work for the TDD loop (step 4) — failing test first where the finding is a missing or toothless test — then re-run the review. This keeps `spdd/prompt/` as the queue of remaining work, so "implement the next prompt" always means the lowest-numbered file there — which is how multi-task stories from `user-story` get executed in order.

## Failure handling

- A test that won't go green after a few honest attempts is information, not an obstacle: re-read the Operation and the surrounding code — the prompt may be wrong (→ step 2 protocol) or your understanding may be (→ read more).
- Never weaken a Safeguard test to make it pass. Never delete a failing test to "unblock" progress. If a Safeguard genuinely conflicts with an Operation, the prompt has a bug — raise it.
- If the suite was already red before you started, tell the user before doing anything; you need a green baseline to trust the TDD loop.
